# ORIN 1.6.0 security migration

Status: implementation and local verification; NOT an activated production security service.
The signed Android review APK bundles the Spark-compatible UI and native lock. It does not point to nonexistent security/model services. The separate security web build is a migration candidate that fails closed without its configured backend. Do not swap these labels or ship an inactive service as enabled.

## What must exist before production activation

1. A trusted Node22 Firebase Cloud Functions runtime (Firebase Blaze/billing) or an equivalent server with Firebase Admin credentials. The current expected `orinSecurity` and `orinApi` endpoints returned404 during this task. No production function, Hosting bundle or strict rules were deployed.
2. Server-only `ORIN_SECURITY_MASTER_KEY`:32 cryptographically random bytes encoded as base64, bound through Secret Manager to `orinSecurity`. This is a local cryptographic secret generated by the operator, not a paid third-party API key. Back it up securely with an access-controlled rotation/recovery plan. Never put it in Vite, APK, source, screenshots or logs.
3. `ORIN_ACCOUNT_SECURITY_ENABLED=true` in server runtime; strict `firebase-security-160.rules`; and server-owned `system/account-security` document `{enabled:true,rulesVersion:160}`. The marker is set only after verifying the corresponding rules deployment. The API rejects marker/flag mismatch instead of silently reverting to password-only access. Do not use a client-side setting as the activation authority.
4. WebAuthn RP/origin: configure the exact supported ORIN HTTPS site as documented in `firebase-functions/ACCOUNT-SECURITY.md`. Passkeys on one RP are not automatically valid on another hostname. Android WebView uses native PIN/biometrics; browser Passkeys are available only where WebAuthn is supported. Native Android Credential Manager passkeys and iOS native biometrics are not implemented in this Android-only project.
5. If a trustworthy end-client IP is needed behind a proxy, verify the deployment's non-bypassable ingress and set its peer allowlist/hop configuration. Until then IP is unavailable rather than presenting a proxy's IP as the user's. City/country needs an operator-provided maintained local GeoIP database or a separate verified GeoIP service; none is configured. GPS is never substituted.
6. The support assistant needs an actual self-hosted vLLM/OpenAI-compatible model server with HTTPS, JSON-schema responses and `/v1/models` plus `/v1/chat/completions`; see `firebase-functions/SUPPORT-AI.md`. It is inactive until server/model health is real. No model key or endpoint is present in the APK. A private gateway token, if used, belongs in server secrets only.

## Authentication-provider boundary — release blocker for the full request

The application uses custom ORIN TOTP/session enforcement layered on Firebase Auth. It protects ORIN API and strict Firestore access. It cannot change the provider's own password-only `accounts:update` or account-deletion authority. A supported provider-level MFA/credential-change policy (such as an appropriate Firebase Authentication with Identity Platform integration) or a reviewed authentication-authority migration must close that path before claiming end-to-end step-up enforcement. Do not assume upgrading a plan alone closes it; test the provider API directly with a password-only token and confirm refusal.

Firebase password verification happens at the identity provider. ORIN authoritatively logs its own successful security logins, second-factor/passkey failures and security mutations; it does not fabricate provider wrong-password failures. A provider audit/event integration or authenticated primary-login gateway is still needed to meet the complete failed-login audit requirement.

The ORIN server checks the provider token-revocation baseline before refresh. Individual ORIN revocation and administrative revocation invalidate server-owned session/epoch state immediately. Existing Firebase bearer tokens and direct provider operations must still be included in provider-policy acceptance testing; a UI logout is not the security boundary.

## Coordinated migration

Keep the existing application and rules intact until runtime prerequisites are available. Deploy a test project with Auth+Firestore+Functions and the strict rules first. Build with `npm run build:firebase-security`, verify security endpoints, create the server activation marker, and test the complete account lifecycle. Then schedule the coordinated production backend, strict rules and client migration; old clients without a session claim will be denied by design. Have a tested restore path, but never leave MFA marked active while reverting data access to password-only rules.

Relevant configuration: `firebase.security-160.json`. Relevant build command: `npm run build:firebase-security`. Native review build: `npm run build:firebase-spark` followed by `python3 android-app/build.py`. The package preserves the existing signing certificate, but signing secrets are excluded from the handoff.

All endpoints require origin validation and no-store responses. Protected requests include both Firebase bearer and `X-Orin-Session`. Real financial transfers/withdrawals remain inactive; action-scoped step-up helpers do not imply that a withdrawal engine has been activated.

## Acceptance still required

- Physical Android8+ and a modern Android device: initial PIN, each0/60/300/900-second timeout,299/300-second boundary, Home/back/recents, kill/restart/reboot, network changes, rotation, deep links/notifications and pending PIN/biometric callbacks after backgrounding.
- Wrong-PIN cooldown survives process kill/reboot; biometric key invalidation/new enrollment falls back to PIN; no financial frame visible before unlock; no PIN/secret in logs or backup.
- Two real clients: per-session revoke and logout-others deny retained tokens, owner/admin revoke, provider password reset and partial network failures.
- Real authenticator enrollment, first-OTP confirmation, replay/clock windows, recovery use/concurrency/regeneration; TOTP toggles invalidate stale grants and trust proofs.
- Real browser platform passkey registration/login/delete, cancellation, RP/origin rejection, lost credential and fallback.
- Live model Arabic/application-grounding tests, prompt-injection attempts, missing knowledge, human takeover, outages, no cross-customer context and no financial mutation.

Local emulator/unit evidence is included under verification. It is not a substitute for these acceptance gates. No customer balances, sessions, TOTP secrets, Auth exports or production database records were used as test fixtures.
